# 数据库迁移策略

## 为什么仓库里没有迁移 SQL

历史迁移脚本（词条批量回填、topic 映射、复核状态写回等）**全部包含生产库内容**——
词条原文、`owner_id`、复核意见。按仓库安全约定（见 README「安全约定」），
生产数据与用户数据一律不入库，因此这些脚本被 `.gitignore` 的 `*.sql` 规则排除，
只保留在本地工作副本中。

## 当前迁移方式

Schema 与数据的变更通过以下途径管理：

1. **云平台控制台** —— WorkBuddy 云服务（genie-baas）控制台直接执行 SQL，
   表结构变更在控制台留痕。
2. **应用内功能** —— 导入、富化、删除等数据变更走应用自身的写入路径
   （`lexiloop/js/store.js`），自带权限校验与冲突处理。
3. **本地运维脚本** —— `tools/` 下的脚本按需在本地运行，操作生产库前需人工确认。

## 后续迁移的提交约定

- **纯 DDL**（建表、加列、加索引，不含数据）可以提交到本仓库，
  命名 `db/migrations/NNN_描述.sql`，并在 `db/schema.md` 同步更新结构说明。
- **含数据的 DML**（INSERT/UPDATE/DELETE 生产行）**不要提交**，
  在迁移说明里记录用途与执行位置即可。
